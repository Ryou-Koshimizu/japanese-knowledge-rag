# ADR 001：全文索引・ベクトル・権限を SQLite の1ファイルに持つ

- 状態：採用
- 日付：2026-10-20

## 背景

社内規程・マニュアルの検索は、1社あたり数百〜数千文書、チャンクにして数千〜数万件の規模が中心です。案件として納めるとき、運用する側の負担（サーバーの数・バックアップ・障害点）を小さくしたい一方で、日本語の全文検索とベクトル検索の両方が要ります。

## 決定

- 文書・チャンク・権限（部署と役職）・埋め込みベクトルを、SQLite の1ファイルに入れる。
- 全文索引は **FTS5 の trigram トークナイザ**（SQLite 3.34 以上、Python 標準の `sqlite3` に同梱）。形態素解析の辞書を持たずに日本語の部分一致ができる。
- ベクトルは float32 の BLOB で保存し、権限で絞ったチャンクだけを内積で並べる（正規化済みなのでコサイン類似度）。
- 権限は `documents.min_role` と `doc_access(doc_id, department)` に持ち、検索のすべての SQL に同じ条件（`store.ACL_SQL`）を入れる。

## 理由

- 追加のサーバーが要らない。バックアップは1ファイルのコピーで済み、CI でも本番と同じ構成で試験できる。
- 1つのトランザクションで「文書の差し替え・索引の更新・権限の更新」が揃う。差分取り込みの途中で落ちても、索引と権限が食い違わない。
- この規模なら、ベクトルを全件なめても1問あたり十数ミリ秒（`docs/evidence/retrieval.json` の `ms_per_query`）。

## 対応範囲と移行先

- チャンクが数十万件を超える規模では、ベクトル検索を近似最近傍（sqlite-vec・pgvector 等）へ移す。`Store.vector_search` だけを差し替えれば済むよう、検索の統合（RRF）と権限の条件は `Searcher` 側に置いている。
- 複数台で書き込む構成では、取り込みを1か所（バッチ）にまとめ、各台は読み取り専用で開く。
